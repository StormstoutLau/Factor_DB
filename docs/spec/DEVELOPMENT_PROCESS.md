# Factor_DB 开发流程规范 (Spec)

> 本文件定义 Factor_DB 项目的标准化开发流程。任何功能开发、Bug 修复、架构改造都必须遵循本规范。
> 核心原则：**先调研、后设计、再实施、必验收**。每一个阶段产出文档，文档之间交叉引用，杜绝"代码与文档脱节"。

---

## 0. 文档制品总览

每个开发任务在 `docs/` 下产生以下制品（按阶段顺序）：

| 阶段 | 制品 | 存放位置 | 必填 |
|------|------|---------|------|
| 1. 调研 | 调研文档 | `docs/research/` | ✅ |
| 2. 设计 | 设计文档 | `docs/design/` | ✅ |
| 3. 实施规划 | 实施文档 | `docs/implementation/` | ✅ |
| 4. 验收准备 | 审查 checklist | `docs/spec/REVIEW_CHECKLIST.md` | ✅ |
| 5. 实现 | 代码 + 测试 | 对应模块 + `tests/` | ✅ |
| 6. 决策归档 | ADR | `docs/adr/` | 架构级变更时 ✅ |

---

## 1. 阶段一：调研 (Research)

### 目标
在不写任何实现代码的前提下，通过多种来源充分理解问题域、现有方案、社区最佳实践。

### 必须使用的 MCP 工具（多源交叉验证）
| MCP 服务器 | 用途 |
|-----------|------|
| `mcp_paper-search` | 学术论文检索（arxiv/pubmed/semantic scholar 等） |
| `mcp_english-search` | 英文网络/PDF/新闻/学术检索 |
| `mcp_research-tools` | arxiv/semantic_scholar 检索 + paper 下载 |
| `mcp_scholar-mirror` | 学术镜像检索、按年份检索 |
| `mcp_stackexchange` | 社区技术问答（StackOverflow 等） |

### 调研要点
- **至少 2 个以上独立来源**交叉验证同一结论，禁止单源断言。
- 明确区分：*事实*（有出处）vs *推断*（需标注为推断）。
- 记录版本号、发布日期、URL，便于回溯。

### 产出：调研文档
文件名：`docs/research/<topic>_research.md`
必须包含章节：
1. 问题定义与范围
2. 候选方案对比（表格：方案/原理/优缺点/适用场景）
3. 社区/学术现状（带引用）
4. 关键结论与推荐方向
5. 参考文献列表（完整 URL/DOI）

### Review 门槛
- [ ] 是否引用了 2+ 个独立来源？
- [ ] 结论是否有出处支撑？
- [ ] 是否标注了"推断"部分？

## 2. 阶段二：设计 (Design)

### 目标
基于调研文档，产出不依赖具体实现的架构/接口设计。

### 设计要点
- 只做高层设计（模块划分、数据流、接口契约），不写实现细节。
- 每个设计决策必须**回溯到调研文档**中的依据。

### 产出：设计文档
文件名：`docs/design/<topic>_design.md`
必须包含章节：
1. 设计目标与非目标
2. 架构图 / 数据流图
3. 接口契约（类/函数签名，不含实现体）
4. 关键决策及依据（引用调研文档）
5. 风险与权衡

### Review 门槛（重点排除幻觉）
- [ ] 每个决策是否都有调研依据？
- [ ] 接口签名是否与现有代码库一致（不臆造不存在的模块）？
- [ ] 是否声称了未经验证的能力/限制？
- [ ] 数据规模、性能指标是否来自实测或可靠出处？

---

## 3. 阶段三：实施规划 (Implementation Plan)

### 目标
将设计文档转化为可执行的工程方案，**逐项排除工程隐患**。

### 必须考虑的工程细节（逐项 check）
| 类别 | 必查项 |
|------|--------|
| **版本** | 依赖库最低/推荐版本；Python 版本兼容；API 破坏性变更 |
| **依赖** | 新增/移除依赖；依赖冲突；是否需更新 `pyproject.toml` / `requirements.txt` |
| **兼容** | 与现有表结构/接口/CLI 的向后兼容；是否破坏已有查询 |
| **接口** | 函数/类签名；参数类型；返回值类型；与调用方的契约 |
| **签名** | 参数名一致性；默认值；`Optional` 标注；可变默认参数陷阱 |
| **低效操作** | 避免 pandas `melt()`（用 DuckDB UNPIVOT）；避免逐行 INSERT；避免全表扫描；避免无索引 JOIN |
| **内存** | 32GB 约束；ART 索引 OOM 风险；分区裁剪策略 |
| **数据一致性** | PIT 语义；`loaded_at` 处理；NULL 空壳行过滤 |

### 产出：实施文档
文件名：`docs/implementation/<topic>_implementation.md`
必须包含章节：
1. 分步实施计划（每步可独立验证）
2. 工程细节逐项结论（上表每一项的明确答案）
3. 涉及修改的文件清单（精确到文件路径）
4. 接口/签名变更清单（Before/After）
5. 测试计划（TDD 测试用例列表）

### Review 门槛（重点排除幻觉与低效）
- [ ] 依赖版本是否核实（而非凭空写）？
- [ ] 文件路径是否真实存在？
- [ ] 是否引入了低效操作（melt/逐行INSERT/全表扫描）？
- [ ] 接口变更是否列出 Before/After？
- [ ] 是否考虑了 32GB 内存约束？

## 4. 阶段四：审查验收准备 (Review & Checklist)

### 目标
在编码前，先定义"什么算完成"，并做文档间一致性对齐。

### 产出：审查验收 checklist
使用 `docs/spec/REVIEW_CHECKLIST.md`（见下），按任务填充具体项。

### 文档一致性对齐（cross-document consistency）
编码前必须检查：
- [ ] 调研结论 → 设计决策 → 实施步骤 三者是否逻辑一致？
- [ ] 术语是否统一（如 `factor_wide` vs `宽表` vs `wide table`）？
- [ ] 数据规模数字是否在各文档中一致？
- [ ] 接口签名在设计与实施文档中是否一致？

---

## 5. 阶段五：TDD 实现

### 铁律
1. **先写测试（红）** → 运行确认失败 → **写实现（绿）** → **重构**。
2. 测试文件命名 `tests/test_<module>.py`。
3. 每个公共方法至少一个 happy-path 测试 + 一个边界/异常测试。

### 实施顺序
1. 写测试用例
2. `pytest tests/test_<module>.py` 确认失败
3. 实现代码
4. `pytest` 确认通过
5. 运行全量回归 `pytest` 确认无破坏

---

## 6. 阶段六：审查验收 (Review & Acceptance)

### 验收标准
- [ ] 全量测试通过（`pytest`）
- [ ] 审查验收 checklist 全部勾选
- [ ] 文档一致性对齐全部通过
- [ ] 关键决策已归档为 ADR（如为架构级变更）

### 验收后动作
- [ ] 更新 `docs/DEVLOG.md`
- [ ] 更新 `docs/adr/`（如适用）
- [ ] 更新 `ARCHITECTURE.md`（如架构变化）
- [ ] 更新 `project_memory.md`（关键决策、教训）
